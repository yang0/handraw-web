## 1. 产品目标与主线

Skill 是开源免费的，难以直接收费。网站的作用是承接 Skill 用户，并提供 Skill 做不到的东西：

- **看得见**：别人用某个编号做出了什么，提示词是什么。
- **省事**：不装 Skill、不配模型，在网页上直接出图、给文章配图。
- **留得住**：作品、收藏、历史、个人库跨设备同步。
- **有反馈**：分享后有人看、有人收藏、有人复刻。

主线保持 `docs/product-direction.md` 的设定，压缩成一条可度量的漏斗：

> Skill 出图 → 一键分享到网站 → 别人看到帖子 → 点「做同款」进入创作台 → 生成 → 分享

收费点放在网站：生图额度、文章配图批量生成、付费资源解锁。Skill 保持免费，作为获客渠道。

### 1.1 现在离这条主线有多远

- **生产环境不是新网站。** `handraw-style.com` 现在仍是 Discourse 加旧插件（`/api/boot` 返回 404），新后端尚未部署。
- **子域名指向了别的服务。** `forum.handraw-style.com` 与 `studio.handraw-style.com` 打开的是标题为「ChatGPT 号池管理」的页面，疑似 Nginx 落到默认站点，把另一个服务的后台暴露在本站域名下。**这条与产品无关，但应最先处理**，见第 8 节。
- **首页没有 Skill 用户的入口。** 首页只有「发现作品 / 开始创作」。Skill 引导页（`?view=skill`）藏在画风页里，文案是「开源扩展与在线创作双向飞轮」「一键跃迁至官网实测与无限画布」这类说法，看不出用户该做什么。
- **分享链路的终点不统一。** Skill 分享落到「作品」，论坛发帖落到「帖子」，两者在网站上是两种对象、两个详情页、三套评论（见第 2 节）。

## 2. 内容模型：一切都是帖子

### 2.1 现状

同一件作品「溪边的小熊与小鸟」在本地有两个详情页：

| | `/forum/?view=resource&kind=work&id=…` | `/forum/?view=topic&id=…` |
|---|---|---|
| 渲染 | `demo/assets/forum-resources.js` | `demo/assets/forum-app.js` `renderTopicDetailPage` |
| 数据 | `GET /api/forum/resources/{kind}/{id}` | 整个 `/api/boot` |
| 点赞按钮 | 「👍 点赞」，不显示数 | 「点赞 (0)」 |
| 评论区 | 「共用讨论」卡片＋「讨论」输入框，同页两块 | 「全部社区交流与调优楼层」 |
| 评论表 | `work_comments` 或 `asset_comments` | `forum_replies` |

画风、图型也走 `view=resource`，评论写进 `asset_comments`。三张评论表由 `backend/forum_resources.py:432-437` 按映射选择，`shared.js:1007` 还在写旧接口 `/api/assets/{code}/comments`。用户在一个页面留言，另一个页面看不到。

从首页点作品还要多跳一次：`main?view=work` 先加载主站，再 `location.replace` 到论坛（`main-app.js:1495`）。每次跳转都重新拉 `/api/boot`、`catalog.json` 与 `options.json`。

### 2.2 目标模型

**帖子是唯一的内容容器和详情页。** 作品、画风、图型、讨论都是帖子，区别只在帖子正文挂了什么。

| 帖子类型 | 正文挂载 | 主要按钮 | 谁能发 |
|---|---|---|---|
| 作品帖 | 成图（多图）、提示词、画风与图型卡片、模型 | 做同款、收藏、分享 | 任何登录用户；Skill 分享 |
| 画风帖 | 画风定义、示例图、复制定义 | 使用此画风、收藏 | 官方与任何登录用户 |
| 图型帖 | 图型定义、示例图、构图说明 | 使用此图型、收藏 | 同上 |
| 讨论帖 | 正文、图片，可选挂作品或资源 | 回复 | 任何登录用户 |

规则：

- **发布与收录分开（决定 F）**：
  - 用户发布的画风帖、图型帖立即在论坛公开，可以被回复、收藏、做同款；
  - 只有通过收录审核的，才和官方资源一起进入「画风」「图型」频道页、首页的「最新资源」以及创作台的资源选择器；
  - 未收录的只出现在论坛列表、作者主页，以及引用它的作品帖里。
- 收录审核沿用现有的双人投票（`backend/curation.py`，D-02），审核对象从「投稿」改为「帖子」。收录后帖子地址不变，只是加上「已收录」标记和官方编号。
- 一个官方或已收录的编号对应**一个**固定帖子，编号即地址：`/t/FB-041`。用户从 Skill 图鉴点编号直达这里。未收录的用户画风使用帖子地址，不占官方编号。
- 作品帖地址 `/t/<topicId>`；`works.id` 只作内部外键（D-01 保留）。
- 回复只有一张表。点赞、收藏、浏览、复刻都按帖子计数。
- 画风帖下方显示「用这个画风做的作品」，数据来自作品帖的 `styleIds`，不再单独维护。
- 讨论帖可以引用作品或资源，引用处显示卡片，点击进入对应帖子。

### 2.3 详情页布局

以现在的帖子页为准（创始人指定的样式），做以下调整：

- 资源帖把「生图提示词」区换成「定义」区，主按钮为「使用此画风/图型」，跳到创作台并预填。
- 作品帖的主按钮统一叫**「做同款」**。现在同一动作有「复现此作品 / 复刻同款 / 一键复刻 / 查看做法 / ⚡ 同款」五种叫法，全部改掉。
- 计数统一显示「点赞 n · 收藏 n · 做同款 n」，点击后立即变化，失败再回滚。现在每次点击都会重拉整个 `/api/boot`。
- 右栏保留作者卡与同板块讨论；画风帖右栏改为「搭配常用的图型」。
- 去掉帖子页的「上一帖 / 下一帖」：按发布时间排序的前后帖对用户没有意义。

### 2.4 数据与接口

- 新增 `posts` 视图层或直接沿用 `forum_topics`，加 `kind`（work / style / layout / discussion）与 `ref_id`（works.id 或资源编号）。
- 画风帖、图型帖增加 `catalog_status`，取值为 `none`、`reviewing`、`listed`、`delisted`。频道页、创作台选择器、首页「最新资源」只查询 `listed` 与官方资源。论坛列表不按这个字段过滤。
- 新增统一回复表 `post_replies`。三张旧评论表停写，旧数据用一次性脚本迁入，迁不过来的放弃（决定 C）。
- 新增 `GET /api/posts/{id}`（含挂载对象）与 `GET /api/posts/{id}/replies?cursor=`，详情页不再依赖 `/api/boot`。
- `curation_resource_topics` 在迁移后只读，最终由 `forum_topics.ref_id` 替代。
- 删除：`forum-resources.js` 的详情与关联页、`main-app.js` 的 `renderAssetDetailPage` 与 `renderWorkDetailPage` 跳转、`/api/forum/resources/*` 与 `/api/assets/*/comments`。旧链接 301 到帖子。

### 2.5 收录编号（决定 G）

用户画风、图型收录后，编号格式为「原系列前缀 + `U` + 三位序号」，例如 `FIU-001`。

| 官方系列 | 用户收录系列 | 序号 |
|---|---|---|
| 画风 `FA`～`FI`，独家 `FX` | `FAU`～`FIU`、`FXU` | 每个系列从 001 起，各自独立 |
| 图型 `SC` `IG` `SB` `IP` `EC`，独家 `LX` | `SCU` `IGU` `SBU` `IPU` `ECU` `LXU` | 同上 |

规则：
- **何时分配**：只在收录通过时分配编号。未收录的画风帖只有帖子地址，没有编号。
- **系列谁定**：作者申请收录时选择系列，审核人可以修改，最终以收录时为准。界面上给出建议：按作者填的「用途、媒介」匹配到最接近的官方系列。
- **编号不复用**：撤下（`delisted`）后编号保留，不分配给别人。帖子和旧链接继续可以访问，只是不再出现在频道页。
- **并发**：编号在收录事务里按「系列内最大号 + 1」分配，`code` 列加唯一索引，冲突时重试。
- **地址**：`/t/FIU-001` 和官方编号一样，可以直达帖子。
- **旧编号**：现在用户资源用的是 `USR-S…`、`USR-L…`（`curation.py:1347` 用随机十六进制，`admin_services.py:1218` 用两位顺序号，两套规则并存）。按决定 C，这些可以直接废弃，不做映射。

需要修改的代码：

| 位置 | 现在 | 问题 |
|---|---|---|
| `backend/curation.py:1347` `_stable_target_id` | 投稿时生成 `USR-S` + 随机十六进制 | 改为收录时分配 `XXU-nnn`；投稿阶段只用帖子 ID |
| `backend/admin_services.py:1218` | 社区资源用 `USR-S` 或 `USR-L` 加两位序号 | 同上，删除这条分支 |
| `backend/services.py:80-82` `_infer_asset_kind` | 按 `^(SC\|IG\|…)`、`^(F[A-Z]\|…)` 前缀判断 | `FIU`、`SCU` 碰巧能匹配，但应改为明确的系列表，不靠前缀碰巧命中 |
| `demo/assets/studio-app.js:5862-5863` | `/#(F[A-Z]-\d{3})/`、`/#((?:SC\|IG\|SB\|IP\|EC)-\d{3})/` | 匹配不到 `FIU-001`，历史记录里的用户画风会丢失 |
| Skill `skills/handdraw-style-prompter/scripts/build_library.py:15-17,663` | `[A-Za-z]{2}-\d{3}` | 收录资源同步进 Skill 时会被跳过 |
| Skill `validate_library.py:52`、`layout_library.py:48` | 只接受两字母前缀 | 会报「Invalid layout ID」 |
| Skill `prompt_style.py:92`、`resolve_reference.py:61`、`style_asset_paths.py:48` | `^([A-Za-z]{2})[-_]?(\d+)$` | 用户输入 `FIU-001` 时解析失败 |
| Skill 图片目录 `images/individual/FA…FI` | 按两字母系列分目录 | 已定：放进所属系列的现有目录，文件名带 `U`，例如 `images/individual/FI/FIU-001.webp`；图型同理放进对应分类目录。`style_asset_paths.py` 按编号前两位找目录，按完整编号找文件 |

建议在网站和 Skill 两边各写一份相同的系列表，例如 `series.json`：列出 `code`、`kind`、`官方/用户`、`名称`，所有解析与校验都从这张表读取，不再各自写正则。

### 2.6 收录后同步到 Skill（决定 H）

收录的用户画风和图型会随 Skill 发版进入 `E:\handraw-style`。用户每次在 Skill 里用到它，都能看到作者，以及一个回到网站的链接。

**申请收录时的同意**
- Skill 采用「MIT 加署名要求」许可（`E:\handraw-style\LICENSE`）。申请收录前，必须让作者明确勾选同意：定义文字和示例图将按这个许可随 Skill 公开发布，任何人都可以免费使用，包括商用；署名使用作者选择的显示名。
- 说明撤下的后果：撤下后，下一个 Skill 版本会移除这个资源；已经发布的旧版本按许可仍可被使用，无法收回。
- 同意记录（时间、许可版本、显示名）存进收录记录。

**投稿表单与 Skill 格式对齐**

| 类型 | Skill 需要的字段 | 网站表单 |
|---|---|---|
| 画风 | `styles.json`：`number`、`group`、`reference`、`generation_name`（英文）、`traits` | 名称、英文名、参考来源、视觉特征、示例图 |
| 图型 | `layouts.json`：`id`、`category`、`name`、`name_en`、`keywords`、`image`、`prompt_file`；`layouts/<id>.md` 中英双语 | 名称、英文名、分类、关键词、中文构图说明、示例图 |

- 英文名和英文构图说明可以由 AI 先翻译，作者确认，审核人复核。
- **视觉特征必须与题材无关。** Skill 的 `style-library-importer` 规定，`traits` 只能写笔触、媒介、光影、空间，严禁写画面里的人物、服饰、道具、场景。网站提交时用 AI 先检查一遍，标出违规的词；审核清单里也加上这一条。不符合的不能收录。
- 参考来源涉及在世艺术家时，按 `attribution.json` 现有做法记录来源链接。

**同步方式**
- 新增 `ops/export_curated_to_skill.py`：读取上次同步以来新增的 `listed` 资源，以及新的 `delisted` 资源。
  - 在 `handraw-style` 的新分支里写入 `styles.json`、`layouts.json`、`layouts/XXU-nnn.md` 和示例图；
  - 运行 Skill 自己的 `validate_library.py` 与 `build_library.py`；
  - 更新 `version.json`。
- 脚本不推送到主分支。由你检查后合并发版，符合 `AGENTS.md`「公开 Skill 仓库保持独立」的要求。
- 每个 Skill 版本同步一次，不做实时同步。
- STYLES.md 和 LAYOUTS.md 新增「用户收录」小节，每条写明「作者 @显示名」，并链接到 `https://handraw-style.com/t/FIU-001`。**这条链接本身就是从 Skill 回到网站的入口。**
- 网站上的帖子显示「已收录进 Skill v1.x」。

**前置条件**：先改完 2.5 列出的 Skill 端正则，否则 `FIU-001` 会被 `build_library.py` 跳过，也会被 `validate_library.py` 拒绝。

## 3. Skill 到网站的转化

### 3.1 入口

- **Skill 侧**：每次出图后的回复末尾，固定附两个链接：「分享到网站」和「在网站看 FB-041 的更多作品」（`/t/FB-041`）。Skill 图鉴（STYLES.md、LAYOUTS.md）里的每个编号都链到对应画风帖。
- **网站首页**：首屏加第三个按钮「我在用 Skill」，进入一页说明：
  1. 绑定账号，得到 Skill 可用的令牌（见 3.2）；
  2. 出图后点「分享到网站」；
  3. 在网站看谁复刻了你的作品。

  这一页替代现在的 `?view=skill`。
- **画风帖**：显示「在 Skill 中使用：`FB-041`」与复制按钮。会用 Skill 的人复制编号即可；不会的人点「在网页上用」。

### 3.2 账号绑定与令牌

现状：Skill 用 `Api-Key` 请求头携带 `users.api_key`。这个 key 明文存库、拥有账号全部权限（`backend/services.py:286-295`），管理员能在后台看到原文（`admin_services.py:2138`）。

改为个人令牌，Skill 与以后的客户端共用：

- **绑定流程（设备码）**：
  1. Skill 或客户端调用 `POST /api/auth/device`，拿到 6 位码和网址；
  2. 用户在浏览器打开网址，登录后确认「允许 Skill 发布作品与同步个人库」；
  3. Skill 轮询拿到令牌，存到本机。

  用户全程不用复制密钥。
- **令牌表** `api_tokens`：`user_id`、`name`（如「Codex Skill · 家里电脑」）、`scopes`、`token_hash`、`last_used_at`、`revoked_at`。只存哈希，原文只显示一次。
- **权限范围**：`publish`（发作品帖）、`library`（读写个人库与收藏）、`generate`（以后客户端在线生图）。默认只给前两项。
- **个人设置页**：列出已授权设备，可以逐个撤销。
- `users.api_key` 停用。

### 3.3 发布接口

决定 B 允许重定义。建议：

```
POST /api/posts        Authorization: Bearer <token>   Idempotency-Key: <requestId>
{
  "kind": "work",
  "title": "...",
  "images": ["/uploads/..."],          // 先 POST /api/uploads（multipart，不再用 data URL）
  "prompt": "用户最初的创作指令，逐字",
  "styleIds": ["FB-041"], "layoutId": "SC-001",
  "model": "gpt-image-1",               // 可选
  "visibility": "public" | "unlisted"
}
→ 201 { "id": "...", "url": "https://handraw-style.com/t/..." }
```

- 重复的 `Idempotency-Key` 返回原帖子，不重复发布。
- `unlisted` 让用户先发不公开的帖子，确认后再公开，降低第一次分享的顾虑。
- 同步修改 `E:\handraw-style\skills\community-share`，删掉 `/api/entries` 与 Discourse 论坛流程中重复的部分。

### 3.4 客户端

`E:\handraw-style\client`（Python）与 `client2`（Node、Pi Agent）都是未发布原型。建议推迟：

- 先让 Skill + 网站跑通分享和复刻，拿到数据：用户卡在「不会装 Skill」，还是「Skill 出图后懒得分享」？
- 如果是前者，网站创作台已经覆盖，不需要客户端。如果是后者，客户端只需做「本机出图历史 + 一键分享」，复用 3.2 的设备码登录与 3.3 的接口，工作量小。
- 不建议客户端再做一套画布或文章配图，那会和创作台重复。

## 3.5 创作台的三种模式

依据：本地 3099 端口实测（数据库副本），桌面 1440px、手机 390px，未登录状态。

### 3.5.1 现状

| | 表单模式 | 画布模式 | 文章模式 |
|---|---|---|---|
| 实际是什么 | 画布里一个隐藏工作流标签页的简化视图（`studio-app.js:10526` `getQuickParts`） | 节点编辑器：风格参数、图片参数、文本参数、选题裂变、循环批量、桥接、输出控制 7 种节点 | 独立的文章存储 `CS.myArticles`，规划时临时构造一张画布图（`studio-app.js:11459`） |
| 数据 | 与画布共用 `CS.tabs` | 同左，存在 localStorage | 单独存储；登录后整表同步 |
| 手机 | 可用 | 不可用：工具箱和鹰眼几乎盖住整个画布 | 底部工具栏被截掉（见 4.1） |

**模式之间的问题**
- **模式名讲的是界面形态，不是用户要做的事。** 用户想的是「做一张图」「做一批图」「给文章配图」，而不是「表单」「画布」。
- **画布和表单之间的设置会丢。** 只有当前标签页正好是「1 个风格参数 + 1 个文本 + 1 个输出控制，且三者相连，输出方式为图文/纯图/套图」时，表单模式才显示它；否则悄悄切到另一个「快速创作」草稿，只弹一句「已打开表单草稿」（`studio-app.js:12328-12331`）。例子：在画布里打开「节气海报极速出图」，它选的是海报模式、主题色 C-15、情绪「诗意、温暖」；切到表单后，这些设置一项都看不到。
- **标签页越积越多。** 每点一次「做同款」就新建一个「同款 · 作品名」标签页（实测从 3 个变成 4 个），从来不自动清理。首次进入画布还会自动打开 3 个预设标签页。
- **偶发空白画布。** 两次实测中，首次进入画布或切换标签页后画布区域是空白的，重新加载就正常（节点实际存在，只是没画出来）。原因没查清，需要复现。

**表单模式**
- **参数比画布少，又不说明。** 画布的风格参数节点有主题色、影调、情绪、留白、受众、业务场景、双画风融合，表单都没有；画布的输出方式有海报模式，表单只有图文、纯图、套图。
- **比例要手打。** 比例是文本框，要输入 `3:4` 这种格式；数量是数字框，最大 200。
- **费用要登录后才知道。** 未登录时只显示「登录后查看免费额度、积分余额与本批预计费用」，按钮是「登录后生成」。
- **看不到最终提示词。** 提示词是 Skill 的核心价值，但表单没有任何地方能看到要发给模型的完整提示词。
- **做同款没有区分主题和风格。** 实测从「梅雨天里的一碗面」做同款，主题框直接填进原作的整段提示词：「手绘风插画，雨中街角面馆，热气腾腾的一碗汤面，暖色灯光，纸张纹理……」。用户想「换个主题再做」，得自己从一长段里分辨哪些是主题、哪些是风格。
- **参考图被保留，但看不到。** 只显示「已保留参考图片，可在高级画布中调整」，在表单里不能查看或删除。

**画布模式**
- **术语门槛高。** 裂变、桥接、循环批量、鹰眼、输出控制，新用户看不懂。节点卡片里还有「风格参数(5项)」「文本参数(45字)」这种内部计数。
- **预设一点就是 100 张。** 「百图矩阵批量生产」预设裂变 100 条、循环 100 轮，按钮写着「循环运行（共 100 张）」，一次点击就是 100 次计费。
- **emoji 很多。** 每个节点、按钮都有 emoji，和网站「暖纸、墨色、朱砂」的设计方向不一致。

### 3.5.2 目标：按任务分入口

把「表单 / 画布 / 文章」换成按任务分的入口，并共用一个「配方」数据结构：

| 入口 | 做什么 | 替代 |
|---|---|---|
| **做图** | 一张或一组（1–8 张）。选画风、图型、主题色，写主题，选数量与比例 | 表单模式；画布的「单图」预设 |
| **批量** | 粘贴一列主题，或者写一个母题让 AI 裂变出 N 个；可以同时选多个画风。生成前用表格预览「主题 × 画风」，确认后排队生成 | 画布的循环、裂变、桥接预设 |
| **文章配图** | 见第 4 章 | 文章模式 |
| 高级画布（只在电脑上） | 保留现有节点编辑器，放进「更多」菜单 | 画布模式 |

**做图**
- **主要区**：画风、图型、主题色三个选择器，加上主题输入框。
- **数量和比例改成按钮**：数量 1、2、4、8；比例 1:1、3:4、4:3、16:9、9:16、2.35:1，外加「自定义」。
- **「更多设置」默认折叠**：影调、情绪、留白、双画风融合、参考图（可上传、查看、删除）。画布里有的参数，这里都要有。
- **「查看提示词」**：展开即可看到要发给模型的完整提示词（由服务端调用 Skill 生成），可以复制，也可以编辑；编辑后按 4.4 的规则原样发送。会用 Skill 的人可以复制到自己的工具里用，这本身也能让他们回到网站。
- **费用**：未登录也显示单价，比如「每张 N 积分，新用户每天免费 3 张」；登录后显示「本次 4 张：免费 2 张 + 2 × N 积分」。
- **结果区**：每张图提供下载、发布、「再来一张」、「换个主题」（保留其他参数，清空主题）。

**做同款**
- 作品发布时，主题和风格参数分开存：作品帖里保存配方（画风、图型、主题色、比例、模式），以及作者原始的主题文字。
- 做同款时，画风、图型等参数照搬，主题框留空，原主题作为占位提示（「原作主题：雨中街角面馆……」），并在框上方显示「换成你的主题」。
- 不新建标签页，直接在「做图」里打开。

**批量**
- 批量上限：单批默认最多 20 张，超过 20 张需要二次确认，确认框写明总费用。
- 表格每一行显示状态（等待、生成中、完成、失败），失败的行单独重试。
- 结果可以整批下载为 ZIP，也可以选几张合成一个作品帖（D-01：多图是一件作品）。

**高级画布**
- 冻结新功能，只修 bug。
- 首次进入不再自动打开 3 个预设，改为显示一页模板库，用户选了才打开。
- 去掉 emoji，术语改成大白话：裂变 →「AI 扩写主题」，循环批量 →「批量」，桥接 →「多尺寸输出」，鹰眼 →「缩略图」。
- 循环节点的数量超过 20 时，同样需要二次确认。
- 手机上不显示入口；从链接直接打开时，提示「请在电脑上使用高级画布」，并提供「用做图打开」的按钮（配方能转换时）。
- 上线后统计使用率。如果高级画布的生成量长期低于总量的 5%，再考虑下线。

### 3.5.3 数据：配方取代画布标签页

- 新增服务端表 `studio_recipes`：`id`、`user_id`、`kind`（single / batch / article）、`style_ids`、`layout_id`、`colors`、`tones`、`moods`、`whitespace`、`ratio`、`mode`、`subject`、`references`、`prompt`、`prompt_customized`、`updated_at`。每次生成记录关联配方 ID。
- 「做图」和「批量」直接读写配方，不再借用画布节点。生成历史中点「再做一次」，就把配方原样打开。
- 高级画布在运行时，把节点图展开成多个配方，再提交生成。只有结构足够简单的节点图，才能「转到做图」，转换不了就说明原因，不再悄悄换成另一个草稿。
- 工作流标签页的 localStorage 保留为离线草稿，服务端以配方为准。

## 4. 文章配图

### 4.1 实测问题

测试文章：279 字，3 个二级标题加一个总结。

**规划**
- **规则写死在前端。** 规划规则是 `studio-prompt-engine.js:1547` 的 `buildArticlePlanData`：一张封面，再给每个二级标题配一张图。这篇短文被规划出 5 张图，「总结」也配了一张。Skill 的 `article-illustration-planner` 要求相邻两图之间至少隔 400 到 500 字，2000 到 4000 字的文章才配 3 到 4 张。
- **所有卡片用同一个图型。** 包括封面在内，全部套用「IG-001 金字塔信息图」，同时又写着「叙事手绘表达，角色神态生动」，两种指令冲突。
- **不判断体裁。** Skill 会区分知识类（图替繁文、保留公式与阈值）和叙事类（意境、情绪停顿），网站没有这一步。
- **提示词是原文照搬。** 卡片提示词把本节正文整段贴进去，比如「日更不等于涨粉……低于 8% ……。。」，没有提炼视觉隐喻，也没有要求把公式 `点赞×1 + 收藏×1 + 评论×4 …` 画进图里。

**生成**
- **改过的提示词会被重写。** 用户在「调提示词」里改过的内容，生成时会被后端当作「主题」交给文本模型重写一遍（`backend/services.py:3037`），用户最终看到的图与他编辑的提示词对不上。
- **文本模型调用在写事务里。** 这次调用发生在 `with db.transaction()`（`services.py:2929`，`BEGIN IMMEDIATE`）内部，超时上限 120 秒（`skill_prompt.py:134`）。调用期间，其他写请求最多等待 10 秒，超时就报错。批量生成 5 张时，可能出错的时间段累计最长 10 分钟。

**编辑**
- **看不到配图位置。** 左侧是 Markdown 源码，配图卡片全部堆在文章末尾，要切到「预览」页才能看到图插在哪里。
- **插入按钮太多。** 每一段后面都有「＋ 在……添加配图」，短文就有十几个。
- **标题没有自动带出。** 标题框提示「留空自动使用首行标题」，规划后仍是 0/64。
- **提示框挡住按钮。** 「已成功规划」的提示框盖住了底部的「规划封面与插图」按钮。手机上底部工具栏放不下，「封面画幅」被截掉。
- **文章以浏览器本地为准。** 文章与规划存在 localStorage 和画布节点里（`studio-app.js` 中 `CS.myArticles` 与 plan node 双写）。登录用户每次保存时，会把**全部文章**提交到 `/api/studio/articles`（`studio-app.js:541-552`），服务端逐篇覆盖写入（`services.sync_user_studio_articles`），不做版本比较。两台设备或两个标签页同时编辑同一篇时，后保存的会覆盖先保存的。

### 4.2 目标流程

```
导入或粘贴 → 正文进入编辑器 → 「规划配图」（服务端调用 Skill 规则）
→ 正文中出现配图位，可增删、拖动、改提示词 → 「生成全部」或逐张生成（显示额度与费用）
→ 预览（公众号 / 小红书） → 导出 Markdown+图片 / 复制到公众号 / 发布为帖子
```

### 4.2.1 计费（决定 J：按张收费）

- 规划和导入不收费，但要登录并限流，因为两者都会调用文本模型（见 4.6）。
- 每成功生成一张配图扣一张的费用。单张重新生成也按一张计费。先用免费额度，用完再扣积分，沿用现有的生图计费与 `studio_quota_reservations`。
- 点「生成全部」之前，弹出确认：「将生成 4 张（已生成的 1 张跳过）· 免费额度剩余 2 张 · 另扣 2 × N 积分」。确认后逐张预留额度。
- 某一张失败时，退回这一张的费用，其他张继续生成，卡片上显示失败原因和「重试」按钮。
- 重复点击不重复扣费：每张卡片的生成请求带上卡片 ID，作为幂等键。

### 4.3 规划改到服务端

- 新增 `POST /api/studio/articles/{id}/plan`，后端读取 `E:\handraw-style\skills\article-illustration-planner` 的规则，交给配置的文本模型。返回结构化结果：
  ```
  { "genre": "knowledge"|"narrative",
    "cover": { "layoutId", "visual", "prompt" },
    "slots": [ { "afterBlock": 3, "reason": "公式段，适合图替繁文",
                 "layoutId": "IG-004", "visual": "天平对比权重", "keep": ["评论×4","关注×8"],
                 "prompt": "..." } ] }
  ```
- 服务端校验间距与数量规则。不满足时直接修正，不只依赖模型自觉。
- 没有配置文本模型时，退回现在的前端规则，并明确提示「未使用 AI 规划」。
- 每张卡片显示 `reason`，用户能看懂为什么在这里配图、为什么用这个图型。
- 全篇统一一个画风与主题色（Skill 规则）。图型可以按卡片分别选。

### 4.4 提示词所见即所得

- 规划阶段由服务端调用一次 Skill，生成完整提示词，存在卡片上。
- 生成时直接使用卡片上的提示词（`promptFromSkill: true`），不再重写。
- 用户编辑后标记为「已自定义」，重新规划时保留（这一点现有逻辑已经做到）。
- 系统追加的内容（比例、安全约束）在卡片上折叠显示为「系统附加」，不隐藏。

### 4.5 编辑器

- 改为正文与配图位混排的块编辑器：配图位就在对应段落下方，显示缩略图、图型和状态。点击展开提示词，拖动可以改位置。
- 段落间的「＋」只在鼠标悬停或聚焦时出现。
- 标题为空时，自动取首个一级标题。
- 底部工具栏在手机上收进「设置」抽屉，只露出「规划」和「生成」两个主按钮。提示框移到顶部，不再挡住按钮。
- 文章与规划以服务端为准，localStorage 只作离线草稿。去掉画布节点与文章列表的双写：文章模式不再借用画布的 graph 结构。

### 4.6 文档导入

现状：`/api/studio/parse-article` 先抽出纯文本，再让模型整理成 Markdown（`backend/document_parser.py`）。问题如下：

- **没有登录与限流。** 匿名用户也能调用，会消耗 AI 额度；请求体上限 20MB（`runtime_policy.py:21`）。
- **失败时悄悄降级。** 没有 key、35 秒超时、JSON 解析失败，都会降级为本地粗排，前端照样提示「已更新正文」。
- **长文被截断。** 超过 32000 字直接截掉。整篇要求一次输出为 JSON，长文容易超出模型输出长度。
- **图片和表格丢失。** 只抽文字，Word 图片与 PDF 表格都没了。
- **原文可能被改动。** 提示词只要求「排版」，没有要求不改原文。

改法（决定 D：所有格式都走 AI）：

1. **鉴权**：要求登录，按用户限流（例如每天 20 次），文件上限 10MB，使用 multipart 上传。
2. **本地先抽结构**：
   - docx 用 python-docx 读取标题样式、列表、表格和内嵌图片；
   - pdf 用 PyMuPDF 按字号和粗体推断标题，提取图片；
   - md、txt 直接读取。

   抽出的结果是带标记的中间文本，图片先上传，用占位符 `![](upload:…)` 代替。
3. **AI 只整理结构**：要求模型「不得改写、删减或增补原文句子」，只做标题分级、合并断行、去页眉页脚与页码。输出纯 Markdown，不包 JSON。
4. **分段处理**：按章节或每 6000 字切块，逐块转换后拼接；做成异步任务 `POST /api/studio/imports` → `GET /api/studio/imports/{id}`，前端显示「第 3/8 段」。
5. **结果核对**：
   - 计算原文与结果的字数差。差异超过 5% 时提示「AI 可能删改了内容」，并提供逐段对照；
   - 用户确认后再写入编辑器，替换前保留旧稿可撤销。
6. **如实说明来源**：「已用 AI 整理」或「AI 不可用，已按原文导入，标题需手动调整」。
7. **复用配置**：`ai-service.json` 由导入、配图规划与提示词生成共用，统一使用 `backend/config.py` 的 `load_ai_config`。现在 `document_parser.py` 和 `skill_prompt.py` 各自拼一遍请求，合并成一个 `ai_client.py`，统一超时、重试与日志。

## 6. 后端架构

### 6.1 已核实的问题

| 问题 | 位置 | 影响 |
|---|---|---|
| 生图时，文本模型调用发生在 `BEGIN IMMEDIATE` 写事务内 | `services.py:2929`、`:3037`；`skill_prompt.py:134` 超时 120 秒 | 文本模型响应期间，其他写请求最多等 10 秒（`db.py:45` `busy_timeout`），之后报「database is locked」：点赞、回复、登录、别人生图都可能失败 |
| `/api/boot` 一次返回所有已发布作品、帖子、回复、作品评论和资源评论，没有 LIMIT | `services.py:789` 起 | 内容增长后首屏变慢；每次点赞后还会重拉一次 |
| 三张评论表 | `forum_resources.py:432-437` | 见第 2 节 |
| API Key 明文存储，拥有账号全部权限 | `services.py:286-295`、`admin_services.py:2138` | 见 3.2 |
| `/api/studio/parse-article` 不需要登录，也没有限流 | `server.py:2420` | 匿名用户可以消耗 AI 额度 |
| 路由都写在 `_handle_post`、`_handle_get` 两个长函数里 | `server.py` 共 2841 行 | 难以维护 |
| 服务端没有 PATCH | `server.py:1604-2078` 只有 OPTIONS、DELETE、GET、POST | 见 5.3 |

### 6.2 改法

- **事务**：外部调用（文本模型、生图网关、文件解析）一律放在事务之外。流程拆成三步：
  1. 短事务：预留额度，生成任务 ID；
  2. 事务外：调用模型；
  3. 短事务：写入结果，或退还额度。
- **接口**：`/api/boot` 只返回当前用户和站点设置。列表与详情各有分页接口：`/api/posts?kind=&sort=&cursor=`、`/api/posts/{id}`。
- **路由**：按现有 `curation_routes.py` 和 `forum_resource_routes.py` 的方式，把路由按领域拆成独立模块，包括 posts、studio、articles、auth、admin。
- **AI 调用**：合并为 `backend/ai_client.py`，供导入、规划和提示词生成共用，带超时、重试、日志和用量统计。
- **数据库**：继续使用 SQLite。WAL 已开启（`db.py:42`），只要写事务足够短，现在的规模够用。等出现写入排队、`database is locked` 报错，或者需要多进程部署时，再评估迁移到 PostgreSQL。

### 6.3 两套系统并存

- **生产环境跑的是 Discourse 插件。** `ops/server-deploy.sh` 只部署 `plugin/`，Ruby 加 JS 共 8665 行：先 `git archive "$commit" plugin`，再软链接到 Discourse 的 `plugins/handraw-community`。
- **新后端没有部署路径。** `backend/` 只有一个示例服务单元 `ops/handraw-v2.service.example`，监听 3080 端口，没有部署脚本、回滚脚本和发布检查。
- **CI 主要检查插件。** `.github/workflows/checks.yml` 会跑 `unittest discover`、插件的 rspec 和插件 JS 的语法检查。`tests/` 里有 18 个 `.cjs`，CI 只跑其中 6 个。
- **结论：** 新后端上线前，要先补一套与插件同等级别的发布流程：备份、按确切提交部署、回滚、发布检查。生产上线后，`plugin/` 只保留只读存档和回退所需的部分，不再开发新功能。

### 6.4 账号与会话

| 项目 | 现状 | 建议 |
|---|---|---|
| 密码 | PBKDF2-SHA256，迭代 120,000 次（`security.py:10`）。兼容导入的 Discourse 哈希（`security.py:37-40`） | 迭代次数提高到 600,000，用户登录时自动升级 |
| 会话 | `sessions.token` 明文存库（`services.py:306-312`）。Cookie 设置了 `HttpOnly`、`SameSite=Lax`，生产环境域名为 `.handraw-style.com`（`security.py:72-79`） | 改为存哈希，与 3.2 的令牌表用同一种做法 |
| 写请求校验 | 带 Cookie 的写请求会校验 Origin/Referer（`runtime_policy.py:115`） | 保留 |
| 第三方接入 | 只有 `users.api_key` | 见 3.2：设备码登录加个人令牌 |

### 6.5 生图与计费

- 数据表：`wallets`（余额、每日免费额度、签到）、`ledgers`（流水，带 `event_key` 防重复）、`studio_generations`、`studio_quota_reservations`、`unlocks`。整体结构合理。
- 生图流程分三步：
  1. `prepare_cloud_generation` 预留额度；
  2. `complete_cloud_generation` 或 `refund_failed_cloud_generation` 结束；
  3. 后台线程 `handraw-generation-reconciler` 每 15 秒处理一次未完成的任务（`server.py:325-345`）。

  完成和退款都检查状态，不会对同一任务既完成又退款（`services.py:3091`、`:3146`）。
- **要改的只有一处，就是 6.1 第一行：** 在 `prepare_cloud_generation` 里，文本模型调用发生在写事务之内。文章配图按张收费（决定 J）后，每张卡片都会走这条路径，所以必须在阶段 0 修好。

## 7. 分享激励

`需求.md` 的目标是激发分享，并让优秀分享脱颖而出。在现有机制（点赞、收藏、鼓励、打赏、悬赏、复刻谱系 `work_forks`、排行 `backend/ranking.py`）的基础上，做以下调整：

- **首要信号是「做同款」。** 有人用你的作品成功生成过一次，才算一次真实复刻（`work_forks` 已经只统计真实生成）。作品排序、作者主页、通知都优先展示这个数。点赞成本最低，权重也最低。
- **及时通知。** 被做同款、被收藏、被回复时，立即通知作者。`notifications` 表已有，需要补充这三类事件。首次被做同款单独发一条，例如「有人用你的作品做出了第一张图」，并附上那张图（得到对方同意公开时才附）。
- **复刻链可见。** 作品帖下方显示「用这个做的」缩略图墙，每张链到复刻者的作品帖。原作者和复刻者都能被看见。
- **作者主页。** 汇总作品、被做同款总数和常用画风。现在 `?view=profile` 已有雏形。
- **精选与收录。** 编辑每周选几件作品，放进首页「本周精选」，并给作者站内额度奖励。用户发布的画风、图型先在论坛公开（决定 F）；进入频道页靠的是收录本身，这就是最直接的「脱颖而出」：
  - 帖子上显示「申请收录」按钮，作者自己点，或者被做同款满 N 次后系统提示作者申请；
  - 收录后，在帖子和频道页上永久署名作者，并通知作者及所有做过同款的人；
  - 收录后可以同步进 Skill 图鉴，见第 11 节第 1 条。
- **不做的事。** 不做积分刷榜，不做签到送曝光，冷启动内容不计入排行（`cold_start_registry` 已经区分）。

### 8.1 老账号迁移（决定 L）

现有基础：
- **导入脚本**：`ops/import_discourse_users.py` 调用 `services.import_discourse_users_batch`，可以重复运行，已存在的用户会跳过。
- **密码哈希**：登录时校验 Discourse 的 PBKDF2 哈希，依次尝试 64000 和 600000 两种迭代次数，用 32 字节密钥（`security.py:37-44`）。校验通过后自动升级为本站格式（`services.py:452-466`）。
- **其他**：发邮件（`features.py`）和找回密码页面（`?view=recovery`）都已具备。

导入代码 `services.py` 约 3400–3500 行有以下问题，迁移前要修：

| 问题 | 位置 | 后果 | 改法 |
|---|---|---|---|
| 没有密码哈希的用户，密码被设成固定的 `handraw123` | `hash_password(plain_pw or "handraw123")` | 任何人知道用户名就能登录这些账号 | 不设密码，标记为「需重设密码」，登录时引导用户走邮件找回 |
| 没有邮箱时，自动编造 `用户名@handraw-style.com` | `rec.get("email") or f"{uname}@handraw-style.com"` | 找回密码的邮件发不到本人；这个地址如果真的存在，邮件会发给别人 | 没有邮箱的账号不导入，或者只导入后锁定，由管理员处理 |
| 用户名去掉了 `.`、中文等字符 | `re.sub(r"[^a-zA-Z0-9_\-]", "", …)` | `li.ming` 会变成 `liming`，用户用原名登录不了；两个账号还可能撞成同一个名字 | 本站用户名规则放宽到与 Discourse 一致，或者保留原名作为登录别名 |
| 用户名或邮箱已存在时直接跳过，不报告 | `if exists: skipped += 1` | 同名但不是同一个人的账号无法区分 | 输出冲突清单，按邮箱判断是否同一个人，人工处理 |
| Discourse 管理员自动成为本站 `admin` | `role = "admin" if is_admin` | 权限范围扩大 | 一律导入为 `user`，管理员在后台手动指定 |
| 每人自动生成 `api_key` | `generate_api_key()` | 产生一批不用的全权限密钥 | 改为 3.2 的令牌表后，不再生成 |
| 导入代码没有测试 | `tests/` 中没有 | — | 补测试：Discourse 哈希登录并升级、没有邮箱、用户名冲突、重复导入 |

导出前还要核对一件事：脚本注释里的导出 SQL 从 `users.password_hash`、`users.salt` 取密码字段，较新版本的 Discourse 可能把这些字段放在别的位置。先用生产 Discourse 的实际表结构跑一次只读查询，确认字段名、哈希算法和迭代次数。

上线步骤：
1. 在 Discourse 上把用户导出成 CSV，放到仓库以外的目录。用完删除，不提交（`AGENTS.md`）。
2. 先导入预览环境的数据库，用 3 到 5 个真实老账号试登录。其中至少包括：一个原密码账号、一个用户名带 `.` 的账号、一个没有本地密码的社交登录账号。
3. 正式切换时，Discourse 设为只读，再做最后一次增量导入，然后切换域名。
4. 给全部老用户发一封邮件：「新网站已上线，用原用户名或邮箱、原密码登录；忘记密码请点这里」。社交登录的用户要先重设密码才能登录。
5. 迁移礼金（现在默认每人 50 积分，`site_settings.economy.discourse_migration_credits`）在用户首次登录时发放，不在导入时发。这样能统计实际回来了多少老用户。
