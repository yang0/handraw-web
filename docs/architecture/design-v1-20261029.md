## 1. 现状核对与前两轮评审勘误

### 1.1 「作品」实际有四种定义，不是三种

【事实】生产流量走的是 Discourse 插件，不是 Python 后端：
- skill 调用 `https://handraw-style.com/studio/api/entries`（`E:\handraw-style\skills\community-share\scripts\conversation_share.py:22-23`），对应插件路由 `plugin/config/routes.rb:31-34`，挂载点是 `/studio`（`plugin/plugin.rb:38`）。
- 插件的 `Publishing.create!`（`plugin/lib/handraw/publishing.rb:73-113`）先建 `Entry`（UUID 作为 `public_id`），再在「实战作品与爆款」版建一个**预览帖**，立即发布，不经审核。这与 skill 的「作品≠帖子」一致，也与 D-01 一致。
- Python 后端没有 `/studio/api/entries`、`/session/current.json`、`/uploads.json`、`/studio/api/boot` 这几个接口：`backend/server.py` 的路由表里没有匹配项，`/studio/` 只返回 `studio.html`（`server.py:1904`）。

【事实】Python 后端内部有三条作品写入路径：
1. `POST /api/works` 调用 `publish_user_work`（`services.py:1641-1644`），再进入 `curation.submit`。`submit` 立即建论坛帖（`curation.py:408-430`，category 固定为 `assets`，`work_id` 为空），但 `works` 行要等两票通过后才由 `_publish_approved` 写入（`curation.py:982-1012`）。这就是「论坛已发布、广场不存在」。
2. 演示或冷启动数据：先有 `works` 行、没有帖子。首条评论到来时由 `ensure_topic` 懒建 `origin='legacy'` 的帖子（`resource_discussions.py:44-61`），评论写进 `work_comments`。
3. 普通帖附作品卡：`forum_topics.work_id` 引用一件已有作品（`services.py:1685-1691`）。这是引用关系，不是主帖关系。

结论：前两轮评审的「三种冲突定义」方向正确，但漏了插件，也漏了一个关键事实：这些冲突只存在于 Python 后端内部，生产上的 skill 链路目前是一致的。

## 2. 设计决策

### 决策 1：作品的身份

- **主键是 `works.id`**（D-01）。新作品的 id 是 UUIDv4 字符串（`str(uuid.uuid4())`）。历史 `work_<hex>` 格式的 id 不改。选 UUID 的理由：以后迁移 Discourse 作品时可以直接沿用插件的 `public_id`，旧回执链接不失效。
- **作品与讨论帖的关系**：只用 `curation_resource_topics` 一张表表达，一行 `(kind='work', target_id=works.id, topic_id)`。主键 `(kind, target_id)` 保证一件作品最多一个主帖（`curation_schema.py:121-128`）。不新增 `works.topic_id`，也不建视图。理由：这张表已经被评论路由、资源详情和 boot 共同读取（`resource_discussions.py:27,70,130`，`forum_resources.py:98-103,155-158`）；再加一份映射会产生两个事实来源。表名保留，文档语义改为「资源与讨论帖映射」。对待办问题「旧映射表怎么处理」的回答：**保留，继续写入，不废弃。**
- `forum_topics.work_id`：在主帖上也写入作品 id，供现有作品卡渲染使用。判断「是否主帖」只看映射表，不看 `work_id`，因为普通帖引用作品时 `work_id` 同样非空。
- **映射表 `origin` 字段的语义**重新定义为「评论存放位置」：`submission` 表示评论在 `forum_replies`；`official` 和 `legacy` 表示评论在 `asset_comments` 或 `work_comments`。新作品一律写 `submission`。理由：现有代码已经按 `origin=='submission'` 选择评论表（`resource_discussions.py:71,133`，`forum_resources.py:164,302,428`，`services.py:1796`）。沿用这个值，B3 的代码回滚后，旧代码仍能正确读出新作品的评论；新增一个枚举值则做不到。来源信息另记在 `works.origin`（迁移 040）。
- **一次分享多图算一件作品**：最多 9 张（首图是封面，另附 8 张），与 skill 的 `validate_work` 一致。超过 9 张返回 400 `too_many_images`，由 skill 拆分。不截断。

### 决策 2：计数归属

| 计数 | 事实来源 | 缓存列 | 写入时机 |
|---|---|---|---|
| 点赞 | `interactions(target_type='like_work')` | `works.likes` | `toggle_user_like`，同一事务 |
| 收藏 | `collections(bucket='works')` | `works.favorites` | `toggle_user_collection`，同一事务 |
| 鼓励 | `interactions(target_type='work', stamp_label='')` | `works.cheers`、`works.stamp_counts_json` | `toggle_user_cheer` |
| 复刻 | 新表 `work_forks` | `works.forks` | 带 `forkOf` 的生成成功完成时（决策 8） |
| 浏览 | 无 | `works.views` 冻结 | 不写入，不展示，不参与排序 |

- 缓存列允许由 `ops/reconcile_social_counters.py`（B1）按事实来源重算。
- `forum_topics.likes/favorites`：普通帖保留原语义（帖子自己的点赞和收藏）。**作品主帖上这两列冻结**：对该帖的点赞或收藏，服务端改记到作品上，帖子序列化时用作品的计数覆盖这两个字段。这样广场和论坛读到的是同一套计数（D-01）。
- `forum_topics.views`、`works.views`：保留列，不删。不再写入、展示或参与排序。API 继续返回该字段，避免旧前端报错。
- **为什么移除浏览数而不实现它**【推断】：访客大多匿名，可信去重需要 cookie 或 IP 指纹；每次浏览写库又与「GET 不写库」冲突。点赞、收藏、复刻、回复已经足够表达热度。代价：失去阅读量展示。以后有独立的事件采集管道时再重开。

### 决策 3：热门排序

全站只有三种排序语义：

| 参数值 | 含义 | 适用对象 |
|---|---|---|
| `newest` | `published_at_ms DESC, id ASC` | 所有对象 |
| `popular` | 按对象类型的热门公式，同分时按 `published_at_ms DESC, id ASC` | 所有对象 |
| `active` | 最近一条公开回复时间（没有回复时取发布时间）降序 | 只用于帖子；即现有 `activityAtMs` |

热门公式（每类只有一个）：

| 对象 | `popularScore` |
|---|---|
| 作品 | `likes + cheers + 2*favorites + 3*forks` |
| 帖子 | `replyCount + likes + 2*favorites`；作品主帖的 likes 和 favorites 取作品的值 |
| 画风、图型 | 引用它的已发布作品数（即现有 `usageCount`） |

- 权重理由【推断】：复刻代表真实复用，成本最高；收藏表示打算复用；点赞和鼓励是轻量认可。周期筛选（`period=week|month|all`）只按 `published_at_ms` 过滤，不做时间衰减。这样结果可以解释，也可以用索引（迁移 040 的表达式索引）。
- **移除**：所有排序里的 `views`；热门分里的荣誉系数（`honor.boost`）和新发加分（`freshBonus`）。理由：`product-direction.md` §5 要求「减少奖励与曝光权重的重复展示」，热门应该只反映真实互动。新人和新作品的曝光交给「最新」以及现有的 `rising` 新人榜。代价：「首发即享必曝」（`services.py:40` 的 `boostText`）不再成立，相关文案在 B4 一并删除。
- 合并的排序：作品浏览的 `favorites`、`cheers` 两个排序合并进 `popular`；首页榜单保留 `composite`（改用 `popularScore`）、`rising`、`forks`，删除 `cheers`。论坛的 `featured/bounty/paid` 是筛选，不是排序，继续保留。画风目录的 `recommended` 与 `hot` 合并为 `popular`；`exclusive` 和 `code` 作为筛选或字母序保留。
- 唯一实现：后端 `backend/ranking.py`，前端 `S.popularScore(kind, item)`（`shared.js`）。两边用同一组测试夹具做一致性测试（§6 B4）。

### 决策 4：评论存储收敛

- **短期（B3）**：新作品的评论写入主帖的 `forum_replies`（因为 `origin='submission'`）。已有 `work_comments` 的旧作品（`origin='legacy'`）继续读写 `work_comments`。`asset_comments` 不动。回滚：旧代码按 `origin` 读取，评论不会丢。
- **中期（B7）**：脚本 `ops/converge_work_comments.py` 把 `work_comments` 复制到对应主帖的 `forum_replies`（`legacy_source='work_comments:<id>'`，迁移 043 防止重复复制），然后把映射的 `origin` 从 `legacy` 改为 `submission`。原表保留，不再写入。回滚：旧代码看到 `origin='submission'` 后读 `forum_replies`，内容完整。
- **长期（下一期）**：`asset_comments` 收敛。前提是先定义「官方资源零评论不进论坛」这条规则在 `forum_replies` 下如何表达。本期不做。
- 复制时先以 `status='migrating'` 插入，再 `UPDATE` 为原状态。原因：`notify_forum_reply` 触发器只在 `INSERT ... status='published'` 时触发（`feature_schema.py:32-39`），这样不会给作者补发历史通知。
- 统一回复长度上限：清洗后最多 3000 字（`services.py:1798` 的现值）。`resource_discussions.comment` 的 800 字上限（`resource_discussions.py:66`）改为 3000，并给 `publish_forum_reply_post` 补上 `sanitize_html`（目前只做 `strip`，`services.py:1798`）。

### 决策 5：审核边界与状态机

| 对象 | 进入公开 | 进入官方目录或精选 |
|---|---|---|
| 作品（免费或付费） | **即时**（D-02） | 精选：本期由管理员单人操作，且禁止给自己加精；双人审核精选在下一期实现 |
| 画风、图型 | 公开预览即时（投稿帖），进入公共目录需要**双人审核**（不变） | 同左 |
| 帖子、回复、评论 | 即时（不变） | 置顶、加精由版主操作（不变） |
| 官方资源 | 管理员后台直接编辑（不变） | — |

- 付费作品即时发布的风险由现有的举报自动暂停（`services.py:2063-2101`）和管理员退款（`/api/admin/unlocks/<id>/refund`）兜底。代价：低质付费作品可能在被处理前先卖出几份。
- 「作品双人审核进精选」推迟到下一期【推断】：它需要在 curation 中新增「精选」这一种 kind，并把作品状态机改两次。本期先让发布即时，避免两件事叠加。
- `moderation.allow_self_review_for_admin` 的新安装默认值改为 `False`（`seed.py:74`）。这个开关只影响加精、置顶等推广动作（`admin_services.py:353-365`），不影响投稿审核（投稿一律禁止自审，`curation.py:765-766,1187-1188`）。已安装站点的值已经写进 `site_settings`，不会被新默认值覆盖；部署说明要提醒管理员在后台手动关闭。
- `moderation.work_default_status` 标记为废弃：代码不读取，配置键保留。
- 冷启动运营要求：开放画风、图型投稿前，每类至少授予两名非管理员审核者。

**作品状态机**（`works.status`）：

```text
(无) --publish_work--> published
published --moderate:pause / 举报达阈值--> paused
published --moderate:hide--> hidden
paused|hidden --moderate:publish--> published
任意 --moderate:delete（作者或管理员）--> 行被物理删除；主帖 -> hidden
published --作者编辑标题、提示词、说明--> published（不重审）
（历史路径）curation 待审 --两票 approve--> published；--admin withdraw--> withdrawn
```

## 3. 技术规格 A：库结构变更

### 3.1 前置：迁移执行器原子化（B0，`backend/db.py:94-122`）

【事实】`executescript` 会先隐式提交，然后逐句执行。如果中途失败，前半部分已经生效，而 `schema_migrations` 没有写入记录；重跑时 `ALTER TABLE ADD COLUMN` 会报 `duplicate column name`，迁移永久卡死。SQLite 的 `ADD COLUMN` 不支持 `IF NOT EXISTS`。

规格：对每个待执行的迁移，把 DDL 和写版本号放进同一个脚本，一次提交：

```python
_NAME_RE = re.compile(r"^[0-9]{3}_[a-z0-9_]+$")
for version, name, ddl in MIGRATIONS:
    if version in existing:
        continue
    if not isinstance(version, int) or not _NAME_RE.fullmatch(name):
        raise RuntimeError(f"invalid migration id: {version!r} {name!r}")
    script = (
        "BEGIN IMMEDIATE;\n" + ddl + "\n;"
        f"INSERT INTO schema_migrations (version, name, applied_at) VALUES ({version}, '{name}', '{now}');\n"
        "COMMIT;"
    )
    try:
        conn.executescript(script)
    except Exception:
        if conn.in_transaction:
            conn.execute("ROLLBACK;")
        raise
```

- `now` 来自 `utc_now_iso()`，格式固定为 `YYYY-MM-DDTHH:MM:SSZ`，不含引号。`name` 经过正则校验，不存在注入。
- 迁移 DDL 中禁止出现事务控制语句（`BEGIN TRANSACTION`、`COMMIT`、`ROLLBACK`）。`CREATE TRIGGER ... BEGIN ... END;` 不受影响。
- SQLite 允许在事务内执行 `ALTER TABLE`、`CREATE TABLE/INDEX/TRIGGER`。
- 对已经卡在半成品状态的旧库，不做自动修复。本地库已应用到 31（核对 `schema_migrations`），不受影响。

### 7.3 直接判为不合格的实现方式

- 以截断、去重、丢弃代替报错（违反 skill 合同中的「不能静默丢图」）。
- 为作品与帖子新增第二种映射（例如 `works.topic_id` 列、`work_topics` 表）。
- 前端或后端出现第二份热门公式，或者在 `popularScore` 中加入本文没有定义的权重。
- 在 `MIGRATIONS` 里执行 `UPDATE` 或 `DELETE` 来修正历史数据。数据修正只能放在 `ops/` 脚本中，默认只读，`--apply` 前先备份。
- 强制覆盖已安装站点在 `site_settings` 中已有的值（例如 `allow_self_review_for_admin`）。
- 为了让测试通过而修改或删除既有断言，但没有在提交说明中逐条写明理由，并与 §6 的「需要修改的既有用例」对应。
