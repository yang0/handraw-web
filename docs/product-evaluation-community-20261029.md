## 一、先纠正一个前提

你的设想是：**skill 用户多 → 搞网站 → 建社区 → 再搞客户端**。

评估后我要先提三件事，它们会改变推进顺序：

1. **客户端不是"到时候再搞"，而是已经有两个原型且都不可分发。** `handraw-style/client`（Python+installer）与 `client2`（Node/Pi Agent）都存在，但 `client2/README.md` 明确写着「不提交、不推送、不是可拷贝到另一台电脑独立发布的完整包」。所以"再搞客户端"实际是"再完成客户端"，这是一项有明确工作量的工程，不是一句话的增量。
2. **网站的分享链路已经内建在 skill 里了。** `SKILL.md` 规定生成后要写 `original-request.txt`、带 `【画风：FA-013】` 这类 ID 标签、通过 `/studio/api/entries` 建 `kind=work` 条目、并给出「分享到网站」链接。**这是你最大的优势**——分享是创作流程的默认终点，而不是事后想到的动作。
3. **但这条链路的默认落点是"作品广场"，不是"社区"。** 这决定了接下来的产品选择（见第四节）。

## 二、网站现在实际有什么

功能全景树（2026-10-27 核对）共 322 个节点：**已有 207、缺失 28、有问题 30、待核验 43、待确认 14**。

**已具备（真实实现，非文档宣称）**：
- 内容层：画风、图型、作品三类资源，各有独立详情页与关联列表，绑定论坛主题共用讨论。
- 互动层：点赞、收藏、评论、鼓励、积分打赏、举报、悬赏托管与结算、复刻。
- 审核层：投稿→双人一致投票→分歧补第三人→申诉→资格体系（style/layout/work 分别计算）。
- 账号层：注册/登录/邀请码、共享会话、钱包账本、通知表（`notifications`，迁移 020）。
- 冷启动：12 个虚构账号、24 帖、31 回复，带 `cold_start_registry` 标记与独立统计。

**确认缺失或薄弱**（我逐项核对了表结构，不是猜测）：

| 缺口 | 证据 | 为什么重要 |
|---|---|---|
| **关注/订阅关系** | 全库无 follow / subscribe 表 | 社区=关系，不是内容。没有关注就没有"回访理由"，用户只能靠首页推荐偶然回来 |
| **版块体系** | `forum_topics.category` 只是字符串，无版块表 | 无法形成"分区归属感"，也做不了版主自治 |
| **层级回复/@提及** | `forum_replies` 扁平单层（topic_id + text） | 对话无法展开，长篇技术讨论会变成一坨 |
| **作者主页的"作品-教程-讨论"聚合** | 有 `idx_works_author`，但无跨内容聚合视图 | 创作者没有"我的主页"，就没有身份沉淀 |
| **通知的社交类型** | 有 `notifications` 表（`feature_schema.py:20`），但未见"被关注/被引用"类事件 | 冷启动通知全是系统类，不产生社交回路 |

**另一个必须先解决的问题**：`curation.css` 是 9 个 CSS 中唯一没有 `prefers-reduced-motion` 的，而 `forum.html` 会加载它；同时 `studio-app.js:2114` 上传原图不经压缩直接写 localStorage，5MB 配额会瞬爆且 `writeJsonStorage` 无 try/catch——**用户看到"已上传"提示，刷新后图片消失**。分享链路的关键一环有静默失败，这会直接杀死投稿意愿。上线前必修。

## 三、核心产品判断

### 判断 1：你现在的设计是「平台严选」，不是「共创社区」

审核机制是：**双人一致投票 + 分歧补第三人 + 48 小时释放名额 + 资格需先有内容被收录**。

这套机制的质量很高——它能保证"进目录的都是好东西"。但它有明确的代价：

- **供给端门槛高**：新用户第一次投稿，要等两位陌生人审完，才能进入目录。这是**抑制早期供给**的机制。
- **审核者从哪来**：资格要求"同类至少一项已被收录"。冷启动期没有已收录内容 → 没有人有资格 → 只有管理员能审 → 形成死循环。
- **矛盾点**：`community-curation-plan.md` 第 6 条写「新投稿不能绕过收录进入目录」，但第 1 条又要求「先产生论坛帖」。结果是**投稿内容先进论坛（公开可见），再等审核进目录**。那真正的门槛只在"进目录"，不在"发出来"。这点是对的——但文档表述容易让人以为发布本身被卡。

**我的建议**：把"发布"和"收录"彻底解耦，并且明确告诉用户：
- **发布到论坛/广场 = 立即生效，任何人可发**（这是社区活力的来源）
- **进入官方目录 = 需要审核**（这是质量的护城河，且应当稀有）
- 审核不该是全员必经之路，而是**少数优质内容被"升级"为官方资源的通道**。

现在的流程把两者混在一起，会让新用户觉得"发个东西好麻烦"。

### 判断 2：「作品广场」和「社区」是两条路，不能同时做

你的 skill 分享链路默认落到 `/studio/api/entries` 的 `kind=work`（作品广场）。这是一个**展示墙**，不是一个**社区**。区别：

| | 作品广场 | 共创社区 |
|---|---|---|
| 核心动作 | 看、收藏、复刻 | 讨论、提问、改进、协作 |
| 成功指标 | 浏览/收藏/复刻率 | 回访率、发帖者留存、回复密度 |
| 冷启动难度 | 低（内容够多就行） | 高（需要有人愿意开口） |
| 匹配你现状 | ✅ skill 已有 367 画风 + 自动分享 | ⚠️ 话题、版块、关系层都还缺 |

**我的判断：先把作品广场做到"能看、能找、能一键复刻"，再用它喂社区。** 因为：
- 作品广场靠 skill 自动分享就能持续产生供给，边际成本趋近于零。
- 社区需要"人与人对话"，在没有用户基数前凭空做出来只会变成空版面——这是这类产品最常见的失败方式。
- 作品广场天然产生"这个是怎么做的？"的问题，而**问题就是社区的第一批帖子**。

### 判断 3：冷启动的 12 个虚构账号是对的，但缺一条"退出机制"

`cold-start-operations.md` 的做法很专业：普通账号样式、`cold_start_registry` 标记、独立统计、可批量下架、不伪造互动数。这在同类项目里属于少见的清醒。

但要补一条：**当真实用户超过某个阈值后，这批内容怎么退场**。现在的 `--pause` 是手动命令，没有触发条件。建议加一个简单规则写进运营文档：真实用户发帖量 > N 时，分批下架冷启动帖，避免"社区里一半是假人"的尴尬被老用户发现。

### 判断 4：「活跃共创」这四个字，目前最大的障碍不是功能，是反馈闭环太慢

一个用户投稿后，要经历：等待系统分配 → 两位审核者投票 → 通过/退回。这期间他没有收到任何"有人看了你的东西"的信号。

而共创社区的核心体感是**"我的东西有人回应"**。建议在审核之外，先做一件很轻的事：
- 投稿后立刻进入论坛公开可见（已是现状）
- **收到第一个点赞/评论时立刻通知作者**（`notifications` 表已存在，只差事件类型）
- 退回时说明"哪一条标准没满足"，而不是只说"未通过"（文档已有"退回理由"，需确认是否真的给到用户）

## 四、建议的推进顺序

**不要按「网站 → 社区 → 客户端」线性推进**，改成按"内容供给"驱动：

### 阶段 0：让分享链路先跑通（当前就该做）

上线前必修项，都是小改动但影响分享意愿：
1. 修上传图片写 localStorage 的配额崩溃（`studio-app.js:2114`）——否则用户分享到一半图没了。
2. 修 `curation.css` 的 reduced-motion（`forum.html` 会加载）。
3. 统一端口：`config/environments.json`/`ops/web.ps1` 是 3000，`service.bat`/README 是 3080，新用户会起错。
4. 把 10 个本地已绿的测试接进 CI——否则分享链路回归了照样能部署。

**验收**：一个 skill 用户从生图到"分享到网站"成功，刷新后作品还在。

### 阶段 1：作品广场做扎实（1-2 周）

先不管社区，把"看作品"这件事做到位：
- 作品详情：成图 + 做法（提示词/画风 ID/图型）+ 关联资源 + 一键复刻
- 作者页：他的作品聚合（目前只有索引，没有聚合视图）
- 搜索：按画风编号、图型、用途找，而不仅是标题关键词

**验收**：陌生人进站，30 秒内能找到一个想复刻的作品并成功复刻。

### 阶段 2：把"问题"变成社区的第一批内容（2-4 周）

在复刻动作上挂一个轻量入口：**"复刻了但效果不对 → 去问作者"**。这一下就能自然产生第一批真实帖子，且这些帖子自带上下文（画风+图型+成图），质量远高于空版面的"大家好"。

同时补三个最基础的关系能力：
- 关注作者（`follow` 表 + 作者页"关注"按钮）
- 通知扩展到社交事件（被关注、被回复、被引用）
- 版块：先把 `category` 字符串提升为一张真正的表

**验收**：一周内出现 ≥5 条由"复刻→提问"产生的真实对话。

### 阶段 3：审核从"全员必经"降级为"锦上添花"（按需）

把现在的双人审核保留，但**只用于"进入官方目录"**这一个场景。普通发帖永远即时生效。这样新用户不会被流程吓退，而官方目录依然稀缺可信。

### 阶段 4：客户端（最后，且要有明确目标）

`client2` 目前是原型。在动它之前先想清楚：**客户端要解决的是哪个网站解决不了的问题？** 如果答案是"批量生成和画布连线的便利"，那它服务的是重度用户；如果答案是"让不会用 AI 的人也能出图"，那它需要完全不同的形态。

**在阶段 1-3 拿到真实用户行为数据之前，不建议投入客户端。** 因为客户端的形态选择（轻量分享 vs 深度创作）取决于用户到底在哪一步卡住，现在没有这个数据。

## 五、最大的三个风险

1. **空社区**：在没有用户基数时先建社区，最可能的结局是"创作者来得少、读者来得更少"，然后团队去填内容，填到疲惫。**对策：让作品广场先跑，用它自动喂内容。**
2. **审核瓶颈窒息供给**：双人审核 + 资格需先被收录，在冷启动期会形成"没人有资格审 → 没人能进目录 → 更没人有资格"的死循环。**对策：解耦发布与收录，见判断 1。**
3. **分享链路静默失败**：上传图配额崩溃 + 无 try/catch，用户以为分享成功实际没有。**这是对创作者信任伤害最大的一种失败**，比功能缺失更致命。**对策：阶段 0 必修。**

---

## 六、需要你决定的三件事

1. **作品广场 vs 社区，先做哪个？** 我的建议是先广场（理由见判断 2）。
2. **审核机制是否降级？** 即"普通发帖即时生效，只有进官方目录才审核"。这会改变 `community-curation-plan.md` 的核心设计，需要你确认。
3. **客户端的目标用户是谁？** 重度创作用户，还是零基础用户？这决定了要先做哪个原型。
